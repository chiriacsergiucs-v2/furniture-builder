# ADR-0004: Legacy localStorage migration is atomic, idempotent and non-destructive

## Context

Users already had projects (`mobila-cutlist:project:*` + `mobila-cutlist:project-index`) and a preset array
(`mobila-cutlist:presets:v1`) in localStorage before ADR-0003. Losing or corrupting those on upgrade is the single
worst outcome for a workshop tool. A migration can be interrupted (tab closed, quota error) and may run on a
device where IndexedDB already holds newer data (e.g. restored backup).

## Decision

On first start the app reads a snapshot of legacy keys, validates each record with the production validators
(`validateProject`, `validatePreset`, `validateResult`), and writes **only missing IDs** into Dexie inside **one
read/write transaction that also writes the completion marker** `metadata['migration:localStorage:v1']`. Existing
Dexie records always win. If anything throws, data and marker roll back together and the migration can simply run
again. **Legacy localStorage keys are never deleted or modified.** Invalid legacy entries are skipped and reported
in `MigrationReport.warnings`, not dropped.

## Alternatives considered

- **Delete legacy keys after successful copy** — rejected by explicit user instruction; keeps a recovery path if an IndexedDB bug is found later.
- **Migrate lazily per record on access** — rejected: no single point to report warnings; harder to reason about idempotency.
- **Overwrite Dexie with legacy on conflict** — rejected: a restored or newer IndexedDB record must not be regressed.

## Consequences

- `readLegacySnapshot` is pure over a `Storage` interface so it can be unit-tested with injected data.
- A cached `lastResult` that fails `validateResult` is discarded from the migrated copy (with a warning); the project itself is still migrated.
- Future migrations must copy this pattern: marker inside the transaction, missing-only writes, no deletion of sources.
- E2E `migration.spec.ts` injects real v1-shaped localStorage before boot; unit `db.test.ts` checks idempotency and collision handling.

## Compliance check

`grep -n "removeItem\|clear()" src/` finds no call against legacy keys; `migrateLocalStorage` contains exactly one `database.transaction('rw', …)` that includes `database.metadata`; `npm run test -- db` passes.
