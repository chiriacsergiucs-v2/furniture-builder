# ADR-0014: The guillotine cut tree is the canonical layout; SVG and CSV are derived from it

## Context

Operators need the actual cut sequence, not just rectangles. A list of placed rectangles cannot prove the layout is
guillotine-feasible or reconstruct cut lines.

## Decision

`BoardLayout.tree: CutTree` (`part` | `waste` | `cut{orientation, at, kerf, first, second}`) is the source of truth
for a board. `placements` are a derived flat view (`collectPlacements`). SVG diagrams draw cut lines by walking the
tree; CSV placement export lists `board, stock, material, part ID, instance, x/y, width/height, rotated` from the
same data. Nothing renders rectangles that are not leaves of a validated tree.

## Alternatives considered

- **Rectangle list + separate cut list** — rejected: two representations drift; the validator could not prove feasibility.
- **Store only cut sequence** — rejected: UI needs direct rectangle access; the tree gives both.

## Consequences

- Export formats are projections; adding a format never adds state.
- Tree node rectangles are absolute sheet coordinates (ADR-0009), so exports need no transformation.

## Evidence (repository files)

- `src/engine/types.ts` — `CutTree`, `BoardLayout.tree`, `Placement`.
- `src/engine/geometry.ts` — `leaves`, `collectPlacements`, `kerfArea`, `countCuts`.
- `src/import-export/svg.ts`, `src/import-export/csv.ts`.
- `docs/architecture.md` — "SVG diagrams derive cut lines from the cut tree, rather than arbitrary rectangle outlines."

## Compliance check

`svg.ts` imports the tree walker, not `placements` alone; the validator (ADR-0012) rejects a board whose `placements` disagree with tree leaves.
