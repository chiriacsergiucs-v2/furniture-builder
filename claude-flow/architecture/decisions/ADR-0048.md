# ADR-0048: A material can show any picture from the user's device; the picture is kept on the device, the design keeps a reference

## Context

The user wants furniture drawn in the look of the board it is made of. They first asked for built-in decors from
Egger, Kastamonu, Fundermax and Kronospan. They then narrowed it to this: any picture they choose becomes the
material's colour and background. Shipping supplier decors would need verified supplier data (ADR-0010). A
picture the user picks needs none. Manufacturer and type labels are deferred to ADR-0049.

## Decision

- **Picture on a material.** `Material.image = { id, name, tileLength, tileWidth, turn? }` (`src/core/types.ts`).
  - The design stores only this reference.
  - The bytes live in the new Dexie **version 5** table `images`. Each row is `{ id, name, type, width, height,
    bytes: ArrayBuffer, createdAt }`, stored as bytes rather than a Blob so every browser can store it. Earlier
    tables are unchanged (ADR-0012).
- **Import** (`src/persist/images.ts`):
  - Accepted: PNG, JPEG and WebP up to 30 MB.
  - The picture is decoded in the browser and scaled down to 2048 px on its longest edge, keeping its
    proportions. It is then stored as JPEG.
  - Anything else becomes a message: wrong type, empty, too large, unreadable, or failing to save. The board keeps
    what it had (ADR-0008).
  - The material's plain colour becomes the picture's average colour. Cut sheets, catalog pictures and the
    fallback use that colour.
  - Nothing leaves the device (ADR-0002).
- **Size on the board.**
  - One picture covers `tileLength` mm along its width and `tileWidth` mm across, then repeats. Both are whole mm
    from 1 to 10 000 (ADR-0003).
  - The default is 1000 mm along the width, with the picture's proportions.
  - The picture's width runs along the part's grain axis. **Turn picture 90°** runs it across instead.
- **Mapping is core code.** `src/core/surface.ts` (`faceMapping`, `boxUvs`, `planeUvs`) turns a part from
  `buildModel()` and the picture reference into texture coordinates per face. On an end face, the picture runs
  along the face's non-thickness axis. The 3D view and the front view only apply them (ADR-0004). Geometry is
  unchanged: the cut list, sheets and checks are identical with or without a picture.
- **Fallback.** A material without a picture, or whose picture is not on this device or cannot be decoded, is
  drawn in its plain colour. The Materials dialog says "not on this device".
- **Projects.** The same board with and without a picture, or with different pictures, are different decors. The
  picture id is part of `materialKey`.
- **Removing.** A board can be removed only when no part uses it (`removeMaterial`). Stored pictures are never
  deleted automatically, because copies in projects and other designs may use the same id.
- **Files carry their pictures** (answer 1). An exported design or project file has a `pictures` array: each
  picture its materials use, as base64 with id, name, type and pixel size (`withPictures`). On import the file is
  validated first. Its pictures are then stored unless the id is already on the device (`takePictures`). A bad
  picture is skipped and reported, and the file still opens with that board in its plain colour. Files without
  `pictures` open as before.
- **Manual cleanup** (answer 2). Library → **Clean up unused pictures** finds pictures that no stored design,
  project or template mentions, and none that the open piece or project uses (`unusedImageIds`). Rows are searched
  as text, so a row the app cannot read still keeps its pictures (ADR-0012). The button says how many it found and
  asks before deleting.

## Alternatives considered

- **Picture embedded in the design as a data URL.** The design file would travel with its picture. But every
  autosave, project copy and undo step would carry hundreds of kB. Rejected for now.
- **Built-in manufacturer decors.** These need verified supplier data (ADR-0010) and were dropped by the user.
  Labels are recorded in ADR-0049.

## Consequences

- Exported files grow by the pictures they carry, usually a few hundred kB each.
- Pictures that no material uses any more stay in the `images` table until the user cleans them up.
- The front-view SVG download uses plain colours (`data-plain`), because picture URLs exist only in the app.

## Compliance check

`npx vitest run tests/surface.test.ts` checks the following:
- files are refused with a message, never a throw;
- the scale-down is correct;
- bad references fail validation;
- the parts are byte-identical with a picture;
- the per-face coordinates are right;
- a version-4 database upgrades with every row kept.

`node tools/materials/find-it.mjs <preview url>` adds a picture from the bare app at 1440 and 375 px and checks
it in 3D and in the front view, offline after a reload.

## Answers (2026-10-24, from the user)

1. Should design and project files carry their pictures, so they show on another device? **Yes, embed the
   pictures.** Built as described in the decision.
2. Should pictures that nothing uses be cleaned up? **A manual button.** Built in Library, and it asks before
   deleting.
