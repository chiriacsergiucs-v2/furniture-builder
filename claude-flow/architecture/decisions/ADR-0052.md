## Context

Research features *Shared material/finish propagation* (rank 12, value 4.6, P1) and its child *Global parameters*
(value 3.2), both Roomle. The paper recommends a scope selector — *This item / Connected run / Entire ensemble* —
instead of an abstract "global parameter". Today each project piece is an embedded copy with its own `materials`
(ADR-0022); changing a finish means editing every piece. The Materials button is hidden in project view
(`{!inProject && …}` in `src/ui/App.tsx`).

## Decision

- **Project → Selected piece → "Finish"**: two choices, *Fronts* and *Carcass*, each a board picker (the boards of
  all pieces in the project, merged by `materialKey`, plus the user's decor list from ADR-0049), and a scope:
  **This piece / This run / Whole project**.
- **This run** = the run the selected piece belongs to, by the same rule as `suggestRunParts` (floor base units side
  by side). Pieces not in a run offer only *This piece* and *Whole project*.
- **Applying** copies the chosen board into each target piece's `materials` (reusing it when the same `materialKey`
  is already there) and sets the root's matching board id (`frontMaterialId` / `bodyMaterialId` on cabinet, corner
  and desk roots, the front board of a `panel` root; wardrobes are cabinets). Roots without that role (frame, panel
  set) are skipped and counted in the result line "Applied to 5 pieces, 1 skipped: bed has no fronts".
  Fillers and covers of affected runs take the new front board; the worktop is not changed.
- **One-time, not linked.** Pieces stay independent copies; a later per-piece change is allowed. Applying is one
  undo step (ADR-0050).

## Alternatives considered

- **Live global parameter** (pieces follow a project-level finish until detached) — needs a link model in every
  piece and a "detached" state; the paper itself says the scope selector is easier to understand.
- **Project-level Materials dialog editing a shared board** — boards are per piece today; sharing would change the
  design document format.

## Consequences

- The project cut list merges boards by `materialKey`, so one finish across pieces becomes one row group as before.
- Picture finishes (ADR-0048) travel with the board copy.

## Evidence (repository files)

- `src/core/types.ts` — `bodyMaterialId`, `frontMaterialId` per root.

## Compliance check

- Unit tests: whole-project apply sets every cabinet's front board and skips a bed with a reason; run scope changes
  only the run; fillers/covers follow; one undo restores all pieces.
- Find-it at 1440 and 375 px: project with two base cabinets and a wardrobe → select a cabinet → **Finish** →
  *Fronts* → pick another board → **This run** → **Apply** → the wardrobe keeps its fronts, both cabinets change
  (3D colour and Parts CSV material column).
- `npm run lint && npm run typecheck && npm test && npm run build`.

## Questions and answers (2026-10-24; recommended answers auto-accepted on the user's instruction)

1. *Linked (live) or one-time apply?* — **One-time apply; pieces stay copies.**
2. *Which roles?* — **Fronts and carcass, chosen separately.**
3. *What is a "run"?* — **The same run as the run parts (base units side by side).**
4. *Do run parts follow?* — **Fillers and covers follow the front board; the worktop does not.**
