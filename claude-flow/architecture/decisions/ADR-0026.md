## Context

The workshop receives supplier cutting templates (Regency "SABLON DEBITARE" workbooks, SALICE order forms). A
wrong column mapping produces wrong cut sizes silently. The original Regency workbook referenced by the code has
never been committed to or inspected from this repository.

## Decision

`readGenericXlsx` detects known English/Romanian column names only. A vendor-specific adapter is implemented
**only after** the original file is available and a field mapping (including the ABS-inclusive vs cut-size policy,
ADR-0010) is written down and approved. Until then `regencyIntegrationStatus` stays `PENDING` and the UI shows the
generic importer. Workbook bytes are never stored in localStorage or Dexie.

## Alternatives considered

- **Infer mapping from column headers seen in screenshots/descriptions** — rejected by explicit user instruction and by the 1 mm error cost.

## Consequences

- TSK-010 produces the mapping spec; only after sign-off does an implementation task exist.
- Any uploaded vendor file for this purpose must be referenced by path/sha in `evidence/source-index.json` before an adapter is written.

## Evidence (repository files)

- `src/import-export/excel.ts` — `regencyIntegrationStatus='PENDING: require original SABLON DEBITARE NOU.xlsx; no inferred Regency column mapping.'`; "Never store workbook bytes in localStorage."
- `docs/data-format.md` — "Regency template layout deliberately remains unimplemented until original workbook is inspected."

## Compliance check

`excel.ts` contains no vendor-named column constants beyond the generic detector; `regencyIntegrationStatus` unchanged until TSK-010 closes.
