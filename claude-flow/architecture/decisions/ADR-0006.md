## Context

With no cloud (ADR-0002) and evictable local storage (ADR-0003), user-initiated JSON files are the only durable
copy. Users already hold per-project `.backup.json` and `mobila-cutlist-presets.json` files from the localStorage era.

## Decision

Three backup formats are supported and kept readable: **project JSON v1** (`schemaVersion:1`, omits cached
optimisation results), **preset-library JSON v1**, and a new **full database JSON v1** (`furniture-builder-full-backup.json`)
covering all six data collections. Imports validate every record first, then merge in a single transaction;
**existing IDs are skipped, never overwritten**. Material or thickness values are never silently migrated on import.

## Alternatives considered

- **Binary/IndexedDB dump** — rejected: not inspectable or editable by the user, not portable across browsers.
- **Overwrite-on-import** — rejected: a user restoring an old file must not lose newer work; conflicts are reported, not resolved destructively.

## Consequences

- Any new collection must be added to the full-backup exporter/importer and to the round-trip test in the same change.
- Backup readers for v1 formats stay in the codebase indefinitely; adding v2 means adding, not replacing.
- UI must surface "export backup before clearing site data or changing devices" (docs/deployment.md).

## Compliance check

Round-trip test: export full DB → import into fresh `fake-indexeddb` → record counts equal; importing the same file twice changes nothing.
