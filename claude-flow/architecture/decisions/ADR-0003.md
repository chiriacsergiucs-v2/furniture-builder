## Context

The original build prompt required "no database" and "all data in localStorage". localStorage is synchronous,
string-only and quota-limited (~5 MB), which blocked a preset library, build kits, materials library and revision
history. On 2026-10-10 the user explicitly approved an exception for **client-side** storage only.

## Decision

Persistent project data lives in **IndexedDB via Dexie 4.2.1** in database `mobila-cutlist-build-kit` with tables
`projects`, `presetCategories`, `presets`, `kits`, `materials`, `revisions` and `metadata`. The "no database" clause
of the original prompt is superseded **only** for local browser storage; ADR-0002 (no remote database) stands.
localStorage is retained solely for the theme preference and as a read-only legacy source (ADR-0004).

## Alternatives considered

- **Keep localStorage, compress JSON** — rejected: still synchronous and quota-bound; no indexes or transactions.
- **Raw IndexedDB API** — rejected: verbose, error-prone versioning; Dexie provides declarative versioned schemas and transactions with a small Apache-2.0 footprint.
- **SQLite-in-WASM (e.g. sql.js / OPFS)** — rejected: large bundle, OPFS support uneven on Android browsers at the time of decision.

## Consequences

- All storage access is asynchronous; UI code must handle pending/failed opens. A database-open failure shows a blocking message and **never** silently falls back to localStorage writes.
- Schema changes require a new Dexie version (ADR-0005). Record-level `schemaVersion` is independent of the Dexie version.
- Unit tests run against `fake-indexeddb` (test-only dependency).
- IndexedDB is device-local and may be evicted by the browser; JSON backups remain mandatory (ADR-0006).
