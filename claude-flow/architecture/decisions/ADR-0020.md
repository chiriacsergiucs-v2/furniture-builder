## Context

The catalogue shows the roadmap (18 families) to the user, but a card without a real generator must never produce
imaginary cuts that could be sent to a saw.

## Decision

`FurnitureTemplate.status` is `'ready' | 'planned'`. `availableTemplate()` and the configurators create parts only
for `ready` entries; `planned` entries render as labelled plans. Promotion to `ready` requires: model and cutlist
dimensions agree, positioned 3D instances are valid, no panel overlap, preset source versions serialise safely
(AGENTS.md B24 rule).

## Alternatives considered

- **Hide unimplemented families** — rejected: the user wants to see the roadmap in-app.
- **Generate placeholder geometry** — rejected: fabricated cut lists are the worst failure mode for this product.

## Consequences

- Current code: 54 `ready`, 2 `planned` entries in `templates.ts` (the type line `status:'ready'|'planned'` is not an entry); the ledger and README agree.
- Readiness is per-template, not per-family (ADR-0021).

## Evidence (repository files)

- `src/furniture/templates.ts` — "Only ready templates can create manufacturing parts. Future kinds stay visible as plans but cannot generate imaginary cuts."; `status:'ready'`/`'planned'`.
- `AGENTS.md` §"B24 expanded furniture templates" — required checks for a new ready recipe.

## Compliance check

Unit test asserts `initialSpecForTemplate` throws/returns undefined for every `planned` ID; `grep -o "status:'planned'" src/furniture/templates.ts | wc -l` matches the documented count.
