## Context

The modular furniture engine must let a cabinet, chest, drawer or desk be composed from reusable parts without
storing executable logic in user data or Dexie, and must keep old saved trees loadable when a generator changes.

## Decision

Component definitions (`core/carcass`, `core/shelf`, `core/compartment`, `core/drawer-front`, `core/back-panel`,
`core/hinged-door`, `core/plinth`, …) are registered in a `ReadonlyMap` keyed by `id@version`. Persisted data
stores only `{definitionId, definitionVersion, parameters, children}`; `getComponentDefinition` rejects unknown
IDs or versions instead of guessing. Changing a generator's geometry or parameters means registering a new version
and keeping the old one.

## Alternatives considered

- **Store generator functions/expressions in presets** — rejected: unsafe to evaluate, impossible to validate, breaks on refactor.
- **Unversioned definitions** — rejected: a geometry fix would silently change every saved preset's cutlist.

## Consequences

- Every new definition ships with a focused unit test and a template or UI path that exercises it (B-ledger rule).
- The registry is the single place a definition can be added; agents must not create parallel "second geometry engines" (backlog Iteration 1 rule).
