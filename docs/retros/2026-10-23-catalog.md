# Retrospective — template catalog (2026-10-23)

## What the user asked (their words)

1. Templates for every listed furniture type, grouped by room, with a toggle to group by type.
2. "Find how to build it and the configurations it can hold to ensure building variations is supported for each."
3. "Add it to the project's *Start From*" and "keep all of them in a **tab called Catalog** where we have the items with
   their default structure and configurations possible."
4. "UI page, with all the items of new furniture templates **editable**."
5. Research DIY configurators, doubt the earlier design, write ADRs for the entire catalog, 1–5 default variants
   (fewest for a bookcase with a back, most for kitchen cabinets).
6. "Implement all pending ADRs."

## What was delivered first, and what was wrong

| # | Requirement | First delivery | Mistake |
|---|---|---|---|
| 1 | Visible in the user's app | Code in two unmerged PRs (#31, #32); the site deploys only from `main` | The user saw nothing. "Not merged, not deployed" was one line at the end of a long reply, with no way to see the work |
| 2 | A *tab* / *page* called Catalog | A modal dialog | Not a tab, not a page |
| 3 | Reachable | Book icon whose label is hidden under 1320 px (`styles.css`) | No visible menu entry on most screens |
| 4 | 100+ items with structure and configurations | 42 family cards; variants nested inside; Start from listed one row per family | Items existed in code but not on screen |
| 5 | Variations supported *for each* | Recliner, office chair, lounger, sectional had nothing to open; bunk bed and cradle locked with no way to unlock | Hard parts relabelled "reference" or "waits" instead of built |
| 6 | Editable on the page | Pencil inside the hidden dialog | Not findable |
| 7 | Verification | Browser script clicked internal selectors and counted cards | It tested the plumbing, not the request: it never had to *find* the Catalog |
| 8 | Honest report | Opened with feature lists | Reported effort, not outcome |
| 9 | Item names | English only, recorded as a "gap" | Left undone |

## Fixes (same day)

- **Catalog is a page** with its own tab in the top bar ("Editor | Catalog 117"), labelled on every screen width, and
  a `#catalog` link.
- **Every item is listed**: 117 items in 42 families, grouped by room (default) or by type, each with the family's
  default structure and configurations, size and part count from the built model, Romanian name, and Open/Add.
  *Start from* (New, Add a piece) lists every item that opens, with search.
- **Every family has an item that opens**: frame shells for recliner, desk chair, flat lounger, sectional main and
  chaise sections; safety-regulated items (bunk bed, cradle) open after the user ticks "I check safety-regulated
  items against the standards myself" (their warning stays).
- **Edit template** on every family, on the page.
- **Acceptance from the user's side**: a headless browser opens the bare app at 1440, 1024, 390 and 360 px and must
  find the visible text "Catalog", see ≥ 100 distinct items grouped by room, switch to by type, open an item into
  the editor, see ≥ 90 items in Start from, and open `#catalog` directly. All pass.
- **Shipped**: merged to `main` and deployed (see the backlog for the deployment check).

## Root causes

1. "Done" was measured as "code exists and tests pass", not "the user can see and use it in their app".
2. Requirements were paraphrased into ADR language (families, variants, dialog) and checked against the paraphrase,
   not the user's words ("tab", "page", "items", "each").
3. Hard parts were avoided by giving them a status instead of building them.
4. Verification used internal selectors, so it could never fail on discoverability.

## Rules adopted (hard, auto-failing) — also in `AGENTS.md` and `claude-flow/memory/decision-guardrails.json`

_Since ADR-050 these rules live in `CLAUDE.md` (Delivery)._

- **R1 Requirement ledger.** Before calling anything done, list every requirement in the user's own words and mark
  each with evidence from the running app the user will use. A requirement that cannot be reached and used there is
  **not done**. Any unchecked or unreachable requirement fails the whole delivery.
- **R2 No avoidance.** Never drop or relabel a requirement ("reference", "waits", "gap", "deferred") to avoid building
  it. If it truly cannot be built, stop and ask before reporting done.
- **R3 Find-it test.** UI acceptance starts from the bare app and locates features by their visible text, at phone and
  desktop widths.
- **R4 Outcome first.** Replies start with where to click and whether it is live; effort and internals come after.
